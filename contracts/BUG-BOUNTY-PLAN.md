# Bug bounty and disclosure plan

> Status: **no paid program is live.** The site says so on
> `/security/bug-bounty`. This document is the plan and the exact copy to use
> when each phase becomes real. Do not publish a reward, a platform link or an
> "audited" badge before the underlying facts exist.

## Phase 0 — self-hosted disclosure (free, do this first)

What is already live:

- `/security/bug-bounty` with scope, out-of-scope list, severity definitions,
  rules (no DoS, no user data, no public disclosure before a fix) and a
  contact (@oakenhood on X).
- `/security` states "no third-party audit, no bug bounty" in plain words.

What is still missing for a credible program:

1. **A dedicated mailbox** — `security@oaken.one`.
   Use Cloudflare Email Routing (free) on the `oaken.one` zone:
   Email → Email Routing → Enable → create a custom address
   `security` → forward to the owner's real inbox. Add the MX/SPF records
   Cloudflare proposes. Test with an external mailbox before announcing it.
2. **A PGP key** — generated by the owner, private key never leaves their
   machine:
   ```bash
   gpg --full-generate-key          # RSA 4096 or ed25519, no expiry or 2y
   gpg --armor --export <key-id> > security-pgp.asc
   gpg --fingerprint <key-id>
   ```
   Publish `security-pgp.asc` at a stable URL and the fingerprint on
   `/security/bug-bounty`. Reports that contain exploit details should be sent
   encrypted.
3. **Safe-harbour wording** — add to the page (only if the owner agrees to it):
   "We will not pursue legal action for good-faith research that stays within
   this scope, avoids privacy violations, denials of service and data
   destruction, and gives us reasonable time to fix before disclosure."
4. **A response SLA** — e.g. acknowledge within 3 business days, first triage
   within 7 days. Publish only what can actually be met.

When 1–4 exist, replace the X-only contact block on the page and add the
fingerprint. Keep "NOT LIVE" for rewards until a pool exists.

## Phase 1 — paid program (needs a budget)

Choose one:

- **Immunefi** (or a similar platform): apply as a project, provide scope,
  severity levels, reward ranges and a funded pool. Platforms typically require
  a minimum pool in the low five figures USD; confirm current requirements with
  the platform, do not copy a number into the site before it is funded.
- **Audit contest** (Sherlock / Cantina / Code4rena): the contest itself acts as
  a time-boxed bounty and produces a public report. This is often the cheapest
  way to get both review and disclosure.
- **GitHub Security Advisories**: free private intake once the repository is
  public. It is not a paid program, but it is a real disclosure channel and can
  run alongside Phase 0.

Before publishing a paid program, decide and document:

- reward tiers by severity (Critical / High / Medium / Low);
- whether duplicate reports share a reward;
- payment currency and chain;
- who judges (us + an independent reviewer for Critical);
- the disclosure window (e.g. 90 days, earlier by agreement);
- whether the scope includes the Bonds/Timelock admin path (it has a different
  trust boundary and should be a separate, explicitly labelled scope).

## What we will not do

- We will not claim a bounty is live, funded or "up to $X" before the funds are
  committed.
- We will not call a source-verification result an audit.
- We will not ask a researcher to sign an NDA that hides a confirmed loss of
  funds from users.
