# OAKEN contracts v2 — deployed on four chains; the site reads both

The live v1 lock contracts are immutable. This directory contains a **fork** of
the two affected contracts with the self-review fixes. v2 is deployed at new
deterministic addresses on all four chains; v1 stays exactly where it is and
remains the only way to claim or revoke a lock created before 2026-10-23.

## Why v2 exists

`contracts/SELF-REVIEW.md`:

- **SR-01 (High, conditional)**: `createLock` / `editLock` update state after
  `token.transferFrom`; a token with a transfer callback (ERC-777 style) can
  re-enter and over-credit a lock, at the expense of another lock of the same
  token. PoC: `test/foundry/ReentrancyPoC.t.sol`.
- **SR-02 (Low)**: `PinkLockAdapter` accepts `msg.value` and has no way to
  return it.

## What changed

| File | Change |
|---|---|
| `contracts/v2/LockVaultV2.sol` | `nonReentrant` guard on `createLock`, `claim`, `revoke`, `editLock`; new error `ReentrantCall`; one storage word `_entered` |
| `contracts/v2/PinkLockAdapterV2.sol` | same guard on `lock` / `vestingLock`; `_refundValue()` returns any attached ETH to the caller and reverts `RefundFailed` if it cannot; imports `LockVaultV2` |

Everything else is a byte-for-byte copy of v1. The fixes do **not** change the
lock accounting, schedule math, ownership model or the no-owner/no-upgrade
stance.

## Regression tests

`test/foundry/V2Fixes.t.sol`:

- the same re-entrant token now makes the whole outer transaction revert; no
  lock is created and no tokens stay in the vault;
- a plain ERC-20 lock still works;
- the adapter returns attached ETH (adapter balance 0, caller balance
  unchanged) and still creates the lock.

Run:

```bash
forge test --match-contract V2Fixes -vv
```

## Site migration (done 2026-10-23)

The migration is dual-read, not a move: v1 has no admin and no migration
function, so old locks can only be claimed, edited or revoked through v1.

- **New locks** go through `PinkLockAdapterV2`; **new launches** go through
  `OakenLauncherV2`. The create and launch pages were switched.
- **Reads cover both vaults.** Lists, token pages, `/me`, the dashboard and the
  home-page counters query v1 and v2 and merge the rows; every row carries a
  `vault` field (`v1` / `v2`) and the UI shows a small `v2` pill.
- **Record URLs disambiguate.** v1 is the default (so every existing URL keeps
  working); a v2 lock's record URL carries `?vault=v2`, and the site's own links
  add it. v1 and v2 share a lock-id space, so a bare id is not enough.
- **Indexer and API.** `src/index-core.mjs` scans v1 and v2 in the same tick
  (one cursor); the `locks` table stores the vault contract per row;
  `src/api-core.mjs` and `src/upstream.mjs` expose `vault`; the packaged
  snapshots are rebuilt from both.
- **Local chain.** `tools/local-chain.mjs` deploys the v2 set at the same
  deterministic addresses, so page-level e2e runs against the same code path the
  live site uses.

The transfer-hook (ERC-777 style) warning on the create page remains: v2 makes
the reentrancy path revert instead of over-crediting, but tokens with transfer
callbacks are still outside the supported set.
