# OAKEN contracts v3 — deployed on four chains; v1 and v2 stay readable

v3 is **v2 plus one clamp in `revoke()`**. It is deployed at new deterministic
addresses on all four chains, and every new lock and launch now goes through it.
v1 and v2 remain exactly where they are, and remain the only way to claim or
revoke the locks they hold.

## Why v3 exists

The unbounded Foundry invariant suite added with v2 found a sequence the v1/v2
`revoke()` did not price correctly:

1. a **revocable** lock partially vests and the beneficiary claims part of it
   (say 50 of 100);
2. the amount is **edited down** to 60 — allowed, because the only guard is
   `newAmount >= claimed`;
3. the vesting curve is scaled by `amount`, so at the same timestamp the new
   60-token schedule has vested 36 — less than the 50 already paid;
4. the creator calls `revoke()`. v2 froze `amount` at `vestedNow` (36) and
   refunded `60 - 36 = 24`, but the vault held only `60 - 50 = 10` for this
   lock. The other 14 came out of **tokens the vault holds for other locks of
   the same token**, and the record showed `claimed > amount`.

No revocable locks existed on chain when the invariant found this. The create
form could still make one; v1 and v2 are immutable and have no migration or
admin path, so the fix was deployed beside them.

## What changed

| File | Change |
|---|---|
| `contracts/v3/LockVaultV3.sol` | `revoke()` computes `frozen = max(vestedNow, lock.claimed)` and refunds `amount - frozen`. The beneficiary was already paid past the current curve, so nothing past that point is refundable. |
| `contracts/v3/PinkLockAdapterV3.sol` | Unchanged from v2 except the vault it imports; the adapter has no `revoke` path. |

Everything else is a byte-for-byte copy of v2 (which is a copy of v1 plus the
`nonReentrant` guard and the adapter's ETH refund). Lock accounting, schedule
math, ownership model and the no-owner/no-upgrade stance are unchanged.

The source is **frozen**: a comment edit changes the Solidity metadata hash, the
bytecode and therefore the CREATE2 address. Any further change belongs in a new
directory with new salts.

## Regression tests

`test/V3.test.ts` (5 Hardhat tests):

- a revocable lock claims, is edited down below the already-vested amount, then
  `revoke()` refunds only `amount - max(vested, claimed)` — the vault balance
  for another lock is untouched;
- claim before and after expiry follows the schedule;
- edit and revoke keep `claimed <= amount`;
- a re-entrant token rolls the whole transaction back.

`test/foundry/LockVaultV3Invariant.t.sol` is the **unconstrained** invariant
suite (4 invariants; edits and revokes are free to interact). The v3 suite fails
when pointed at v2 (the failing sequence above) and passes on v3; the v1
invariant suite is frozen and only exercises states v1 can handle, with a note
pointing at the v3 suite.

## Site and indexer

The migration is multi-read, not a move:

- **New locks** go through `PinkLockAdapterV3`; **new launches** go through
  `OakenLauncherV3`.
- Lists, token pages, `/me`, the dashboard, the home-page counters and `/verify`
  read **v1 + v2 + v3** and merge the rows. Every row carries a `vault` field.
- Record URLs disambiguate with `?vault=v3` (and `?vault=v2` for v2). No
  parameter still means v1, so every old URL keeps working.
- `src/index-core.mjs` scans all three vaults in the same tick; the `locks`
  table stores the vault contract per row; `src/api-core.mjs` and
  `src/upstream.mjs` expose `vault`; packaged snapshots are rebuilt from all
  three.
- `tools/local-chain.mjs` deploys the v1/v2/v3 sets at the same deterministic
  addresses, so page-level E2E uses the same code path as the live site.

v1 holds every lock created before 2026-10-23; v2 holds locks created
2026-10-23 → 2026-10-24; v3 holds everything after that.
