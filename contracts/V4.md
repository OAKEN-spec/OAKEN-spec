# OAKEN contracts v4 — the upgradeable lock stack (deployed 2026-10-24)

v4 is **v3 behind an ERC1967 proxy**. It is the first lock version with a repair
path; v1, v2 and v3 are immutable and remain readable for the locks they hold.

## Why v4 exists

The v3 self-review found SR-04: a revocable lock that is partially claimed,
edited down and then revoked could refund more than the vault held for that lock,
taking tokens from other locks of the same token. v3 fixed the accounting, but
the deeper lesson was that an immutable vault cannot be repaired. v4 keeps the
v3 accounting and adds a **deliberately slow, public upgrade path**:

- a **2-of-3 multisig** (`OakenMultisig`) owns a **DelayedProxyAdmin**;
- an upgrade must be scheduled, waits **48 hours** on-chain, can be cancelled,
  and emits an event;
- the admin can replace the vault/adapter implementation, but cannot move a
  lock's tokens, change a schedule, pause the vault, take a fee or rescue funds.

The lock-level permission model is unchanged: the only privileged actor over a
lock is its creator (revoke, and only for a revocable lock).

## Upgrade model (what an auditor should attack)

1. Can a 2-of-3 transaction schedule an implementation, change the delay, or
   change the owner without a second confirmation? (The multisig requires two
   distinct owners; `DelayedProxyAdmin` accepts only its owner.)
2. Can `executeUpgrade` run before the 48h eta, after a cancellation, or twice?
   Can a re-entrant implementation call back into the admin?
3. Does the proxy's admin path remain independent of the implementation? The
   five admin functions live in the proxy; only the admin may call them; the
   admin cannot fall through to implementation code.
4. Does an upgrade preserve the vault's storage (locks, `_nextLockId`, guard) and
   the adapter's (`vault` address, per-token/per-owner indexes)? The storage
   layout is documented in `contracts/v4/README.md`; a mock upgrade test adds a
   field and checks all of it.
5. Can an implementation be initialised directly, or a proxy re-initialised?
   Both implementations disable their own initialisation in the constructor; the
   proxy's initializer runs atomically in the proxy constructor.
6. Can a malicious implementation drain the proxy? Yes — that is the trust the
   upgrade key carries. The review should state it plainly: a compromised 2-of-3
   quorum plus 48h is the risk, and the delay is the exit window.

## Tests

- **Hardhat 138** (129 v1–v3 + 9 v4 upgrade-path tests): proxy wiring,
  one-shot initialization, non-admin refusal, lock/claim through the adapter
  proxy, 2-of-3 + 48h schedule/execute, cancellation, non-owner refusal, vault
  upgrade preserving locks, adapter upgrade preserving indexes, launcher through
  the proxy.
- **Foundry 20** fuzz/invariant tests remain the v1/v3 adversarial suites (the
  v4 accounting is v3 and the proxy layer is exercised by the Hardhat tests).
- **Local upgrade E2E** (`_look/v4-upgrade-e2e.cjs`): the real multisig path
  with two impersonated owners, a too-early execution, a 48h warp, an
  implementation swap, preserved locks and a new lock after the upgrade.
- **Real-chain E2E**: a v4 page lock → claim (8 criteria) and a v4 launcher
  launch (13 criteria) on Robinhood Chain, with the transaction reaching the
  adapter proxy.
- **Sourcify**: all seven v4 contracts are exact matches on all four chains.

## Site and indexer

New locks and launches use the proxies. Lists, token pages, `/me`, the dashboard,
`/verify` and record pages read v1–v4; record URLs carry `?vault=v4`. The indexer
scans all four vaults in one tick. Record pages for v4 state the upgrade model;
v1–v3 record pages state that the vault is immutable.

## Honest limits

- **Upgrade risk is real.** A compromised quorum can replace the code after 48h.
  There is no on-chain vote; the delay is visibility and an exit window.
- **No rescue, no pause, no fee switch.** The upgrade path is not a backdoor to
  user balances.
- **Old locks cannot be upgraded or moved.** v1–v3 are immutable.
- **No third-party audit.** Sourcify verification is not an audit; the audit
  package and self-review are separate documents.
